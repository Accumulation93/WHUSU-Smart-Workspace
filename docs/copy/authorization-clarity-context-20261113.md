# 权限查询、分配与审批申请展示设计

本文件是独立逻辑设计，不是最终产品语料。用户本轮明确将“授权身份”改称“权限角色”；协议中的 scheme、工作角色与人事身份类别仍各自独立。语言 Agent 负责最终标题、状态、提示及空态。

## 1. 已核实的事实

1. `server/src/core/services/authorizationExplanation.js` 遍历完整能力目录。返回值不是当前角色已持有权限列表，也不是针对具体记录执行 evaluate 的结果。
2. `conditional` 表示当前角色命中一条有效允许规则。组织范围与指定记录范围都会得到同一个状态；字段全被保护时仍可能存在允许规则。因此不能译作“全部可用”，也不能泛称每项均有额外条件。
3. `business_check_required` 同时表示超级管理员固有权限和仅由业务关系可能产生的资格。后者可能来自目录定义的 businessRoles，并未核对当前人是否实际有一条待办、自己的申请或其他具体业务记录。
4. `denied` 包含无允许、整项明确禁止、普通岗位不能持有治理能力、账号不可用及配置异常。这些原因不能一律解释为管理员没有分配。
5. `web/src/views/admin/AuthorizationView.vue` 的 effectiveGroups 默认隐藏无规则 denied，输入搜索却重新纳入这些条目。小程序同类逻辑必须同时修正。用户目前不能判断自己看的是目录还是已授权集合。
6. `shared/authorizationPresentation.js` 的 recipientCards 已按 assignments:id / adminGrants:id 分组，并非自然人合并；但标题以姓名为主，所有 grants 外卡平铺，只有最终详情折叠。动态 assignmentScope 不进入人员卡，单看默认首页会遗漏这类分配。
7. inspection 已为每条规则返回 displayFields，按被查询角色排除受保护字段，原 fields 保留协议语义；scopeDirectory 仅含引用的维度名称。不能为了丰富说明额外读取业务记录标题。

## 2. 查询状态模型

应分离“授权来源事实”和“某条记录是否允许操作”。本页只有前者，不新增针对任意记录的模拟判断。

| 展示分类（逻辑名） | 真实依据 | 默认明确授权集合 | 限制 |
| --- | --- | --- | --- |
| 超级管理员 | reason=super_admin | 是 | 表示身份提供权限，不断言每条业务记录可执行 |
| 已配置允许 | 存在有效 allow，且非整项禁止 | 是 | 展开实际范围、字段、期限与来源；不贴通用条件提示 |
| 允许并有禁止限制 | 有 allow 和 deny，且非整项禁止 | 是 | 展开分别显示允许与禁止，不把全部范围合并成允许 |
| 整项禁止 | reason=explicit_deny | 否 | 是明确阻断，不混作没有配置 |
| 无显式授权 | 无有效 allow，非上述异常 | 否 | 若存在业务关系资格，只陈述没有显式授予，不声称实际业务一定不可操作 |
| 不适用于当前工作角色 | reason=governance_role_required | 否 | 全目录可解释，不能提供普通岗位治理授予入口 |
| 查询无法确定 | invalid_policy/account_unavailable 等异常 | 否 | 独立错误/不可用状态，不能算普通“未授权”数量 |

主 Agent 最终确认仅提供“已授权 / 全部权限”两个范围，默认显示明确授权集合。全部目录中保留无显式授权、明确禁止及不可用的不同状态，不新增更多平级选项。搜索始终在选定范围内筛选，清空搜索不会改变范围。数量必须按当前范围计算。

超级管理员不要展示几十项相同“还需业务条件”；每项展示其固有权限依据即可。对于有规则的条目，范围与字段本身就是事实说明，不再增加“符合业务办理要求”等不能指导操作的句子。对于仅 businessRoles 产生的可能性，可以在完整目录中区分其授权来源，但不能默认混入已配置允许列表。systemControlled 内部管理动作继续与普通业务项分隔，不将旧键说成实际分配资格。

最小实现可用当前 reason 与 rules.effect 推导分类；若后端增加结构化字段，必须保留旧 status/reason 兼容并由 shared 统一呈现。不能改变 evaluate、业务责任检查或现有许可结果来得到更好看的状态。

查询层级保持业务模块 → 操作项 → 来源与限制，默认折叠。操作摘要只含操作名和一项有明确事实的状态。展开来源时隐藏重复能力名称，保留允许/禁止、范围、可展示字段、期限。没有来源无需空详情容器。

## 3. 分配首页结构

一级按工作角色展示，岗位完整标签为主标题，姓名为副标题；管理身份使用真实管理身份描述。继续使用岗位/管理授权主键，不按同名或自然人合并。摘要展示分配条数，默认全部折叠。

展开一级卡只列权限角色及自定义授权摘要，每条是第二级可折叠行。默认不展示长能力列表、全部范围或大段解释。展开第二级才出现功能、实际记录范围、字段、期限与操作按钮。编辑按钮独立事件，不连带折叠父项。搜索按姓名、工作角色、权限角色和功能筛选，不能自动展开全部长内容。

动态条件分配没有固定成员集合，应在同一首页提供独立折叠分组，用规则名、动态对象摘要与条数呈现；不能展开条件为当前人员再把这些人误当永久授权对象。该分组复用已获许可返回的 rules，不扩大候选目录。

权限角色目录也采用摘要折叠：角色名、已发布/草稿状态、功能数为外层；展开看已发布功能与尚未发布变更。普通使用者可用已发布版本不取决于其能否编辑越界草稿。分配资格属于高级管理，保持与使用权限分离。

## 4. 审批具体申请去除条件组展示

已定位以下具体申请消费点：

- 网页 `web/src/views/AuditSubmissionView.vue:99` 的 approverDesc 与 `:100` 的 ApprovalConditions；前者同样由 buildConditions.summary 生成，必须一起移除，不能只删组件留下条件组摘要。
- 小程序 `miniprogram/subpackages/audit/pages/submissionDetail/submissionDetail.wxml:233` 与 `:234` 当前审批说明；`:307` 下一步条件说明；`:391` 流程节点 approverDesc 与 `:421` 条件组件。

具体申请保留步骤名、动作、状态、真实经办人及岗位、意见、时间、附件与允许的办理按钮。删除条件解释不删除后台 conditions、指定审批人选择、候选过滤及责任判断。

以下是配置/创建阶段，不可机械删除：小程序同文件 `:54` 自由创建步骤，`:73` / `:74` 模板步骤预览，`:522` / `:523` 编辑模板预览，`:547` / `:549` 自由步骤编辑。它们需要让配置人知道已指定谁或何种岗位；模板管理 `AdminAuditTemplatePanel.vue`、`AuditConditionEditor.vue` 和共享 auditConditionView 保留。最终具体申请和配置阶段边界须由主 Agent 确认后实施。

## 5. 验证要求

- 用同一返回数据分别验证默认、全部、无显式授权、搜索及清空，结果范围不隐式变化。
- 覆盖 super、允许组织范围、允许指定范围、允许与局部禁止并存、整项禁止、只有业务关系入口、账号不可用、普通岗位治理限制。
- 人员同名、同人多岗、长权限角色、动态条件、多个来源规则必须可区分；折叠/编辑/批量选择不能互相触发。
- 查询 displayFields 继续使用服务端投影；记录类型数量不附带隐性业务读取。
- 审批具体申请没有条件组及其摘要，配置入口仍能维护条件、候选与实际保存不变。
- 两端共用层检查与三档现场结果分别记录；设计文档不表示实现或设备验证通过。
