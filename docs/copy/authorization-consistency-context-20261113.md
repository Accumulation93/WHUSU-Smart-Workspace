# 权限管理第二轮：完整任务链与一致性设计

独立前端逻辑设计复核，2026-11-13。本文基于当前源代码，不沿用上一轮“入口修好即整体完成”的判断。不修改产品代码和运行语料；具体措辞由独立语言 Agent 放行。实施前须再读最新代码，本文的当前缺陷描述不是后续修复完成证明。

## 1. 已确认的业务模型

用户明确保留“授权身份”：一个方案对应一种授权身份，它独立于人事身份类别和实际工作角色。授权身份保存功能集合；把它分配给岗位或管理身份时，才同时确定业务记录范围、资料项和生效时间。

业务使用权和分配资格是两件事。普通岗位可以使用被授权业务；获得有效分配资格后，也可以在指定边界内分配业务权限。普通管理员并非自动获得分配资格。超级管理员维护分配资格和系统治理，普通岗位不因委托变成管理员。当前工作角色独立计算，不合并同一人的其他岗位或管理身份。

## 3. 已批准的统一结构

主页维持三个主要任务，不为了填满界面增加概念。只显示当前角色能做的任务。普通无分配资格角色默认进入本人权限；受托者与超级管理员默认进入分配任务，授权身份维护独立，查询任务按本人/他人资格分区。超级管理员的分配资格管理放在明确高级管理区的独立业务卡，不混入被授予的使用权限列表。

| 当前角色 | 本人权限 | 分配授权身份 | 维护授权身份 | 查询他人 | 设置分配资格 |
| --- | --- | --- | --- | --- | --- |
| 超级管理员 | 可查 | 全部允许范围 | 创建/草稿/发布，保留事务检查 | 可查 | 可管理 |
| 只有业务使用权的管理员 | 可查 | 无 | 无 | 仅单独获准时 | 无 |
| 获有效分配资格的管理员 | 可查 | 一项资格内 | 按资格及关联影响 | 仅单独获准时 | 无 |
| 获有效业务分配资格的岗位 | 可查 | 一项业务资格内 | 按资格及关联影响 | 不因分配自动获得 | 无 |
| 只有业务使用权或无显式授权的普通岗位 | 可查 | 无 | 无 | 无 | 无 |

本人页面分开显示“可使用的权限事实”与“可分配的资格事实”，不能把同一张功能清单用于两种含义。未知、失败、无显式授权、业务条件待核实必须区分。

## 4. 常用分配流程与控件约束

1. **确定分配资格。** 非超级管理员先选 delegationOptions 中的一项。只有一项时自动选中，但名称和边界摘要始终显示；多项不合并。改变资格时处理已有未保存输入，不能悄悄把旧对象和新范围拼接。资格摘要包含名称、可授权对象、可分配功能、记录范围、资料项、起止。
2. **确定使用者。** 显式资格使用共享人员选择器，一岗一卡或管理身份一项；候选只属于当前资格，排除当前操作者。动态资格使用继承条件，不转换永久编号；可以选择父条件的子集、增加限制，不得移除父维度或扩大值。完整继承会命中操作者时不能直接保存，必须收窄到不含本人的对象或说明当前选择不可用。
3. **确定授权身份。** 只展示当前已发布能力被同一资格完整覆盖、且适合已选角色类型的身份；治理身份不提供给岗位。允许维护但尚无发布身份时提供前往维护的次级路径，不把空列表称为系统失败。草稿内容不参与此次分配。
4. **确定记录范围。** 受限资格继承其范围，允许的收窄方式才展示。records 本轮可完整继承只读，显示已解析名称或明确的可读数量及类型，不显示原始 ID。组织范围等常用选择两端使用相同选中与取消行为；选组织范围时不要让用户误以为叠加“本人”会进一步收窄，多个范围实际是或关系。
5. **显示剩余限制。** 委托限制的资料项和生效时间直接进入常用表单摘要，默认继承；不能把有限期资格初始化成无限期。没有权力扩大时不显示“全部/不限”按钮。自定义/禁止与额外条件放末尾或独立入口，不放在第一步前打断任务。
6. **核对并保存。** 预览必须显示实际选中资格及使用者、身份发布版、范围、字段、期限；预览不写入，确认时事务重新复核。失败保留可修改输入，撤权/切角色后清理失效资格，不自动重放。

## 5. 授权身份与资格管理

授权身份页面分别说明草稿、发布和分配的关系。列表明确当前发布版本与未发布草稿，不把草稿功能套在发布版本标签下。修改已有身份的发布操作会更新全部关联规则，不限于当前列表可见对象，因此需逐条权限检查，任一越界整体拒绝；只读/不可发布的情况在操作前说明。恢复历史版本遵循相同检查。

内部管理动作 systemControlled 仅覆盖 authorization.rules 的 read/create/update/delete、authorization.schemes 的 read/create/update/publish/restore、authorization.delegations 的全部动作。authorization.effective.read 和 authorization.schemes.share/receive 有实际独立检查路径，不一并隐藏。新身份不能新增受控动作；历史身份原值只读展示且明确其不决定分配资格，允许兼容保留但不得复制到新对象形成新增权限。具体历史保存策略由服务端约束，界面不得自行删值。

超管设置资格按“负责人 → 允许授权给谁 → 功能 → 记录 → 资料项/生效期”排列。负责人的标题旁先解释这是分配资格，不直接给予使用权。岗位与管理身份仅是工作角色类型，界面任务结构一致；治理功能仅管理身份资格可选。受领者、最终使用者和业务记录范围是三个不同对象，不能共用一个泛称“人员”或“范围”的控件标题。

## 6. 已与主 Agent 确认的服务端数据

`management` 将返回：canManage、canInspectOwn=true、canInspectOthers（有效可查候选非空）、canManageDelegations=isSuper；delegationOptions 每项含 id/name/version/envelope；catalog 条目可含 systemControlled。只读本人返回空管理列表和目录，不因缺少他人查询资格返回403。

`access` 将新增 canInspectOwnAuthorization（enforced 时为真）、canInspectOthersAuthorization；旧 canInspectAuthorization 保留原他人含义兼容，不能把它改成所有用户可写。选择某一资格的客户端状态不是授权证明，写事务仍以服务端最新完整边界核查。

查询详情需要额外明确最小展示数据：只读本人不能调用完整编辑候选目录；服务端应提供解释中已引用字典/记录的可读名称或受限展示目录。不能把缺少展示索引的正常引用显示成“选项已失效”。

## 7. 验证要求与当前状态

必须分别验证四类角色的入口与任务一致性，尤其只有使用权的管理员不能分配、普通岗位可查本人、有委托岗位能合法分配、两者不自动得到他人查询。真实隔离数据库覆盖限定资料项/期限继承后的前端参数保存回读、多资格不拼接、指定记录继承、动态对象收窄、切资格失效、自授权与治理越界、发布和恢复的全关联检查。

前端需覆盖默认任务顺序、空身份、草稿与发布版不同、性质筛选、两端范围按钮一致性、本人/他人查询详情、长姓名和长记录名称；手机、Pad竖屏、Pad横屏分别验证。本记录仅设计与代码事实，新的前端和后端尚未全部实施验证，不表示完整CI或发布完成。
