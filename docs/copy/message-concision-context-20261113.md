# 通知与待办精简结构设计

本稿为独立逻辑设计，不提供产品定稿。事实来源为 shared/messageFactsView.js、shared/locales/zh-CN/messageFacts.js，两端门户及消息行共用展示函数。

## 层级

业务原始名称优先作为标题，不能为了简洁删去申请名称。没有业务标题/编号才用类型标题。说明表达结果或待办动作，详情行只容纳尚未表达的步骤、时间、地点、原因。若类型标题已经完整表达结果，不再机械重复同一结果说明。去重按结构化业务字段与类型判断，不分析后端中文，也不以任意字符串包含关系删除信息。

## 十四类通知

| 类型 | 保留内容与精简策略 |
|---|---|
| submission_approved | 名称、完成结果、真实轮次；不展示待处理当前步骤 |
| submission_progress | 名称、简短进展状态、已通过/转交步骤及名称；说明不再重复编号。当前步骤与转交相同编号且同名时省去当前行；不同或信息更完整必须保留，不能用当前状态伪造历史转交 |
| submission_rejected | 名称、驳回状态、驳回步骤、原因、轮次；说明不再重复步骤编号 |
| booking_approved | 名称、通过状态、场地、完整借用时间，各一次 |
| booking_rejected | 名称、驳回状态、场地、时间、原因，各一次 |
| booking_cancelled | 名称、取消状态、场地、时间，各一次 |
| hr_profile_approved | 名称（如有）、通过状态；无业务名时类型标题已能承载状态，避免重复段落 |
| hr_profile_rejected | 名称（如有）、未通过状态、原因，避免同状态标题正文重复 |
| hr_profile_migration | 名称或迁移类型、真实事件状态、来源/目标组织；没有事件才标明当前状态，不混成历史动作 |
| score_activity_started | 活动名称、开始状态、截止时间；无名称时避免重复类型标题 |
| score_deadline_24h | 活动名称、一次截止时间；事件时间和当前时间不能混淆。可以保留现有单句，不再新增重复详情行 |
| score_results_published | 活动名称、已发布状态；截止时间对此结果通知无动作价值，不继续附带。权限仍由服务端判断，无需每卡重复权限套话 |
| calendar_reminder | 名称、一次完整时间、地点/场地。时间已可展示时不再用说明重复开始时间或全天；仅一端时间时保留已知端，不猜另一端；确实无时间时保留缺失状态。场地与地点完全相同只留一行，不对不同内容强行去重 |
| account_security | 类型或名称、真实恢复事件；未知类型不捏造动作，不读取后端系统句子 |

各类型原因只出现一次；来源组织、角色和发送时间属于卡片元数据，不再重复拼进正文。无法打开详情的说明保留一次，不重复要求点击不存在的入口。fallback unknown 描述不得引导不可用详情。

## 四类待办

| 类型 | 必需概览 |
|---|---|
| audit_approval | 申请名称、提交人、待审批动作、当前步骤与名称；避免标题无名称时再次重复待审批 |
| venue_approval | 借用名称、借用人、待审批、当前步骤、场地、一次借用时段 |
| scoring_task | 活动名称、真实待评分数量、截止时间；未知数量不写0，0不写还有任务 |
| hr_profile_review | 成员姓名、资料待审核动作；不能从业务标题推断人名，缺姓名明确保留通用任务 |

## 实施与验证边界

不修改通知产生、删除、自动失效、权限、接口事实或时间格式协议。语言角色决定简短状态与缺失说明的自然表达，独立实施接语料。两端模板只有description非空才渲染，避免删文字却留空白。

验证十四通知、四待办，有/无业务名、有/无事实、可打开/不可打开；日程完整/单端/全天/无时间；进展next/current相同与不同、同编号不同名；结果通知不残留截止时间；原因与角色、组织仍可见。还应检查真实浏览器及原生多卡片布局，不能只断言字符串不存在。
