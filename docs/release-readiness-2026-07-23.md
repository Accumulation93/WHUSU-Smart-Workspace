## 樱顶大会议室规则消失的根因

问题不是单一前端显示故障，而是数据边界与异步竞态叠加：

1. 场地本身是全局对象，但审批流程按组织保存。43 届有启用中的流程、2 个步骤及规则；44 届没有对应流程和规则。
2. 旧界面的“借用规则”实际可以由审批流程步骤合成展示。页面此前并发请求传统借用规则和审批流程，传统规则先返回时会在审批流程尚未到达前完成合成，因此 43 届也可能偶发显示为空。
3. 44 届不仅受前端竞态影响，数据库中也确实缺少审批流程；仅修前端无法恢复其内容。
4. 44 届现有人事名称与 43 届并不完全一致，不能依赖名称完全相同做不受控复制。

已实施：

- 前端将流程与规则加载串行化，并通过统一展示函数合成，消除先后顺序竞态。
- 新增幂等迁移 `20260723180000_restore_44th_venue_approval_flow.sql`，按明确映射从 43 届恢复 44 届的流程、步骤与规则。
- 新增迁移集成测试，验证首次恢复、重复执行和已有 44 届配置不被覆盖。
- 场地审批规则改为最小授权和 fail-closed：空的指定范围、损坏条件或越权对象均不能扩大审批权限。

“流程恢复迁移”不是小程序里的按钮或菜单，而是服务端发布时由迁移账本自动执行的一份 SQL。它只在 44 届尚无流程时复制 43 届配置，并按名称将部门、工作组和身份重映射到 44 届；如果 44 届已经有流程则完全不覆盖。当前文件仅存在于本地工作树，生产仍运行旧提交，所以用户此前在界面里看不到迁移，也不会在生产数据库里看到它的结果。

使用本地修复后的前端连接当前服务端进行实机复核时：

- 切到 43 届，“樱顶大会议室”显示“已配置 2 步组织专属审批流程”。
- 切到 44 届，明确显示“当前组织尚未配置专属流程；可新增‘用户审核’规则进行设置”和“暂无组织专属规则，当前由有权限的管理员处理”。
- 复核后已切回 43 届。上述结果证明前端竞态与空白提示已修复，同时也证明当前生产数据库的 44 届确实尚未执行恢复迁移。

## 关键深度修复

### 组织竞态

所有请求以 `{ orgId, role, token, version }` 为同一不可拆分上下文。切换组织、切换角色、重新登录或解绑时版本递增；旧请求即使晚返回也不能提交到当前页面。评分任务、结果弹窗、场地规则、审核详情等高风险入口均应用了这一语义。

### 租户隔离

新增审计器从全部 SQL schema 自动识别组织域表，不再只检查人工列出的少数表。每条直接访问组织表的 SQL 必须包含组织边界，确需全局读取的认证或后台 worker 操作必须进入显式且可审阅的例外清单。

### 授权 fail-closed

审批条件缺失、枚举未知、显式 JSON 损坏、指定范围为空、父子对象不属于同一组织或同一发布时均拒绝，而不是降级为“所有人”或旧配置。

### 数据完整性与性能

评分记录和答案增加业务唯一约束；场地查询加入组合索引；公示子规则批量加载；通知采用有界并发；分页统一限幅，避免无界查询和内存过滤。
