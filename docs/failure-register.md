# 已经踩过的坑，和现在防止它再出现的东西

### 坑 60：整套语言镜像进入主包，产生大量主包未使用 JS

原因：共享语言同步把网页专用 web.js、三个退役语言模块和分包专用文案一起镜像进主包；原检查只确认副本一致和路径可解析，没有从真实入口核对上传归属。公共业务组件及工具也有相同问题。

修复：网页专用和退役文案不再生成小程序副本；按 app.js、主包页面、全局组件及分包页面的真实依赖分配上传资源。仅分包使用的公共组件、工具和文案由唯一维护源生成分包副本，维护源逐文件排除上传，引用指向同包或真实共用的主包模块；不增加虚假 require，不关闭微信质量检查。详见 docs/miniprogram-package-resources.md。

检查：scripts/miniprogram-package-resources.js 已接入共享同步检查，拒绝主包未使用 JS、无入口 JS、被排除依赖、跨分包引用和不同步副本。server/test/miniprogramPackageResources.test.js 覆盖两分包共用、组件注册、注释伪引用、动态 require 拒绝、文案原样复制、篡改拒绝和归属变更恢复。原 UI、组织生命周期、页面注册和微信真实编译仍须通过，不以静态图代替实体设备现场验证。

## 一、界面上的坑

### 坑 1：滚动容器没有固定高度，列表滑到底不加载、弹窗拖不到底

你会看到什么：人事成员目录只显示前 50 个人（实际 785 个人），怎么往下滑都不出新的人；长弹窗里的内容拖不到底，最后一行被切掉。

为什么：微信的 `scroll-view` 只有在高度被限定住时才会自己滚动。之前为了修“弹窗拖不到底”，把几个滚动容器的高度限制去掉了，容器就跟着内容一起变高，内部没有可滚动空间，“滚动到底”这个事件永远不会发生。

现在靠什么防止再发生：
- 必须跑的检查：`node scripts/dialog-scroll-contract-audit.js`（长列表弹窗必须有固定高度）。
- 必须跑的检查：`node scripts/hr-profile-layout-test.js`（滚动到底的处理函数不能是空的；容器没有固定高度的页面必须注册页面的 `onReachBottom`）。

怎么判断又犯了：新做的分页列表，滑到底有没有反应。

### 坑 2：弹窗关掉之后，页面有一部分不能用

你会看到什么：警告、确认这类弹窗弹过一次之后，页面有一块滚不动、点不动。

为什么：页面靠“某个弹窗开着”这个开关来禁止页面滚动（`page-meta` 的 `overflow: hidden`）。开关没被关回去，页面就一直不能滚。

现在靠什么防止再发生：必须跑的检查 `node scripts/dialog-keyboard-audit.js`——每个这类开关都要有写回 `false` 的地方；带输入框的弹窗页面必须声明 `dialogLockKeys`，并在页面卸载时统一关掉。

### 坑 3：键盘弹出来，页面被顶偏，弹窗和按钮错位

你会看到什么：点输入框、手机键盘弹起，整个页面往上跑，弹窗和底部按钮跟着错位，甚至够不到；手机上（尤其鸿蒙）最明显。

为什么：输入框默认会让整个页面上移，而弹窗固定在屏幕上、不跟着走。全站 87 个输入框、23 个多行输入里，当时只有 1 个关掉了“整页上移”，所以必然错位。

现在靠什么防止再发生：必须跑的检查 `node scripts/dialog-keyboard-audit.js`——弹窗里的输入框必须写 `adjust-position="{{false}}"` 并带 `cursor-spacing`；带输入框的弹窗页面必须把键盘高度写进 `page-style`，由 `app.wxss` 让弹窗缩到键盘上方，被挡住的字段靠弹窗自己滚动看到。

### 坑 4：控件被切掉、看不到底、把高度写死

你会看到什么：最下面一格被挡住、勾选框看不见、文字被截断、按钮文字不居中。

现在靠什么防止再发生：必须跑的检查 `node scripts/ui-control-completeness-test.js`、`node scripts/ui-audit.js --strict`、`node scripts/button-alignment-test.js`。不允许写死高度把内容切掉，不允许用一行文字冒充完整的选择框，也不允许把会变化的内容写成固定值。

### 坑 5：文案毛病（写死在代码里、短句、说错对象、把内部词给用户看）

现象举例：“请稍后重试”这种没有对象的短句、“字段”这类内部说法出现在界面上。

现在靠什么防止再发生：必须跑的检查 `node scripts/user-visible-copy-audit.js --strict`、两个 `--strict-localization`、`--strict-guidance`、`node scripts/copy-quality-audit.js`。文案要一条一条按语言习惯改，不许用脚本批量替换。

## 二、服务端和数据上的坑

### 坑 6：启动时的数据检查把全站打成 502

你会看到什么：2026-10-03 12:29:28 到 12:39:33，全站 502 共 226 次，手机提示“暂时无法登录”；自动回滚也起不来，服务停在维护状态。

为什么：管理员表里有一条记录没有对应的有效权限记录。服务启动时会检查这件事，检查不过就拒绝启动。

现在靠什么防止再发生：这类“只是显示用的记录对不上”的问题，启动时先自动补一次；补不上只记一条警告、不让服务起不来。只有真正的结构问题（缺列、缺表）才允许拒绝启动。历史脏数据由迁移文件 `server/db/deploy/*_admin_grant_legacy_link.sql` 一次性修好，迁移记录可查。

### 坑 7：在小程序里正常新建超级管理员，留下一条没有对应权限的记录

你会看到什么：当时看不出问题，下一次重启就触发坑 6，全站停服。

为什么：权限表有一条唯一约束（同一个人 + 同一个组织只能有一条）。写入撞上这条约束时，代码只更新了人、组织、等级，**没有把新记录挂上去**，新记录就永远没有对应权限。

现在靠什么防止再发生：
- 写入语句撞上约束时，必须把关联字段一起更新（`legacy_admin_id = VALUES(legacy_admin_id)`）。
- 必须跑的检查：`server/test/adminGrantLegacyMapping.test.js`（覆盖写入、启动自补、迁移三件事）。
- 每次新建或修改管理员之后，“没有对应权限的记录数”必须为 0，查法：
  `SELECT COUNT(*) FROM admin_info ai LEFT JOIN admin_grants ag ON ag.legacy_admin_id=ai.id AND ag.status='active' WHERE ag.id IS NULL`。
- 一个已确认的事实：管理员表里“学号 + 组织”是唯一的，所以同一个人在同一组织不可能出现两条记录，这个毛病只会表现为“没有对应权限”。

### 坑 8：一升级就停服

你会看到什么：只要有服务端改动，升级就伴随停机。当天 294 次失败里，285 次来自故障和重启窗口。

现在靠什么防止再发生（都写在 `server/scripts/deployProduction.sh` 里）：
- 不破坏结构的迁移（加列、建表、建索引、回填数据）在服务运行时执行，只多做一份一致性备份，不停进程、不进维护状态。
- 破坏结构的迁移（删表删列删数据、改名、改字段类型，或文件里写了 `-- @destructive`）和时间体系切换，才进维护窗口。
- 切换流量之前，先在另一个端口把新版本跑起来、连上迁移后的数据库、访问健康检查；不通过就放弃这次发布，线上完全不受影响。
- 切换用 PM2 的滚动重启（两个实例轮流换）。
- 在线发布失败时，滚动切回旧版本，不停进程、不回滚数据库。
- 只改前端的发布不许重启进程。
- 实测结果：14:39 和 15:53 两次服务端发布，失败请求都是 0 条。

### 坑 9：依赖漏洞公告让 CI 失败

现象：npm 发布了 `braces` 的安全公告，CI 的依赖检查直接失败。

现在的做法：优先升级或换掉依赖（当时用 Node 自带的 `--watch` 替换了 nodemon，整条有问题的链路直接消失）。不许为新公告写豁免；只有“官方没有修复版本、而且这条代码在本项目里根本走不到”才允许豁免，并且要写清证据和到期时间。

### 坑 10：日期和时间

你会看到什么：数据库格式的日期（`Fri Oct 20 2006 08:00:00 GMT+0800`）迁移时不被识别；日期字段显示时带着时间和时区；我复盘时把时间整体说早了 8 小时。

规则：日期解析统一用 `miniprogram/utils/hrProfileDate.js`。日期字段只显示日期（`2004.08.31`），日期时间才显示到秒。数据库存的是 UTC 原始值，展示时按系统配置的时区换算，不许用设备本地时区。必须跑的检查：`node scripts/time-system-audit.js --strict`。查生产时间线必须看数据库原始值再自己加 8 小时，不要直接看程序打印出来的时间。

### 坑 11：超级管理员被显示成“无权限”

你会看到什么：超级管理员进管理端看到“暂无管理权限”，之后又变成一直“正在加载”。

为什么：判断权限的过程里有几处悄悄返回、错误被吞掉；判断“工作角色是否被切换”时连版本号一起比较，真机存储慢一点、版本号变了就被当成换了角色；权限数据在“组织信息还没存下来”时被整份丢掉。

规则：权限判断必须得出明确结果（有权限或没权限），不能停在中间状态；比较会话只看组织、角色、上下文和令牌，不看版本号；只有“确定知道当前组织、且和返回的组织不一致”时才丢弃权限数据；必须有超时保护和一次重试。

### 坑 12：人事资料以组织内为准

规则：成员资料、成员列表、本人资料都读当前组织的记录。跨组织只做复制迁移，源组织的数据保持不变。全局补充资料已经退役（归档后物理删除），不许再往全局写。

### 坑 13：账号、登录会话、设备识别

规则：口令和微信是同一个账号的两种登录方式。所有业务、权限、消息、附件都只用登录中间件给出的账号自然人和当前有效的工作角色来判断操作者，不许再用 OpenID、姓名、学号或客户端人员编号去查“现在是谁”。登录设备只看本地持久保存的安装编号的服务端摘要；保存不了时不许说“这是同一台设备”。冻结、恢复要求、离任、岗位失效对两种登录方式同时生效。

### 坑 14：保存和提交必须用真实参数回读

规则：修保存或提交，必须用真实的前端参数跑通一次，再把保存结果读回来确认。只验证“空参数会被拒绝”“语法检查通过”“函数存在”都不算验收。必须跑的检查：`node scripts/submission-reference-audit.js`（含 `--self-test`、`--inventory`）。

### 坑 16：换成自绘顶栏之后，页面底部多出一段空白、贴顶内容钻到顶栏下面

你会看到什么：页面滚到底还能继续往下拖一段空白；贴在最上面的提示条、Pad 横屏会吸顶的页签，往下滚的时候钻到顶栏下面被挡住；下拉刷新时看不到任何刷新中的反馈。

为什么：`app.wxss` 里 `.page` 的高度是 `min-height: 100vh`。用微信原生导航栏时，`100vh` 指的是“去掉导航栏以后的高度”；顶栏改成自己画以后，页面盖住整屏，`100vh` 变成整屏高度，再加上顶栏的占位块，底部就多出顶栏高度的可滚动空白。`top: 0` 的固定元素同理，现在是从屏幕最顶端开始算，正好落在顶栏下面。

现在靠什么防止再发生：
- 必须跑的检查：`node scripts/native-navigation-test.js`——每个页面必须声明自定义导航、注册并渲染 `<ui-navbar title="{{...}}">`、最外层容器写 `min-height: calc(100vh - {{navTopPx}}px)`，JS 里维护 `navTopPx`。
- 必须跑的检查：`node scripts/ui-navbar-test.js`——顶栏几何、标题、返回键、左侧槽位，以及顶栏层级必须低于全屏弹窗遮罩（顶栏 `z-index` 必须大于 50 且小于 98）。
- 规则：贴视口顶部的固定元素和页面级吸顶元素，`top` 要加上 `navTopPx`；用下拉刷新的页面给 `<ui-navbar refreshing="{{navRefreshing}}">`，因为微信自带的转圈动画会被顶栏挡住。

怎么判断又犯了：随便进一个页面，滑到最底看能不能拖出一段空白；往下滚的时候看贴顶的条有没有被顶栏吃掉。

### 坑 17：复杂弹窗贴在顶栏上，顶部的标题和关闭键点不到

你会看到什么：恢复码、认证码展示和评分详情这类较大弹窗，打开后顶边正好和最上面那条任务栏对齐，弹窗顶部的关闭键点了没反应；手机上尤其明显，鸿蒙机型几乎必现。

为什么：三件事叠在一起。一是弹窗外壳曾经用“顶部贴边 + 底部贴边”来撑高度，这种变体直接把顶边放在屏幕最上面；二是外壳的居中锚点是屏幕正中，高度上限只减掉了安全区，而安卓（含鸿蒙）在网页里读到的安全区是 0，减不掉真实状态栏的高度，于是弹窗越长顶边越往上跑；三是微信右上角那个原生胶囊按钮永远盖在页面最上层，弹窗标题行正好落在它后面就点不动。三套高度和定位规则互相覆盖，越改越乱。

现在靠什么防止再发生：
- 唯一几何来源：弹窗的位置和高度只在 `miniprogram/app.wxss` 里定义一次（`--ui-dialog-top-reserve` / `--ui-dialog-bottom-reserve` / `--ui-dialog-available`），页面和组件一律不得再写自己的 `top / bottom / height / max-height / transform`。
- 顶部安全线取三者最大值：页面写入的自绘顶栏高度、`状态栏 + 顶栏行高`、以及胶囊下沿兜底 `--ui-dialog-capsule-floor`（108px）。只靠前两者不够：页面写入的高度在弹层里不一定生效，安卓和鸿蒙读到的安全区又是 0，二者都会让顶边落到胶囊下面。胶囊下沿各机型最高约 91–97px，108px 这条底线保证任何机型都躲得开，第一版只让位到顶栏高度时用户仍看到“和右上角省略号有一点重叠”就是这个原因。
- 必须跑的检查：`node scripts/ui-audit.js --strict`——居中锚点必须是“去掉上下留白后的可用区中心”，裸 `top: 50vh` 和页面局部覆盖都会被判失败；弹窗里的 `calc(100vh - …)` 也会被判失败。
- 必须跑的检查：`node scripts/dialog-scroll-contract-audit.js`、`node scripts/dialog-keyboard-audit.js`——长列表仍有确定高度可滚，键盘高度仍然参与底部让位。
- 必须跑的检查：`node server/test/auditWorkflowContract.test.js`——外壳定位、按下不变形的契约。

怎么判断又犯了：打开认证码、恢复码展示或评分详情，看顶边有没有比任务栏再低一点；点顶部的关闭键能不能关掉；把正文拖到底看最后一行是不是完整露出来。

### 坑 18：免认证接口只加进一份清单，被组织上下文拦成 401

你会看到什么：网页版点“退出登录”，提示“请重新选择组织和工作角色”，登录状态清不掉；换浏览器重开还是原来的账号。同样的问题也会出现在任何新增的公开入口上——登录、认领、恢复这些老接口之所以正常，只是因为当初两份清单都补了。

为什么：服务端有两份各自独立维护的免检清单，一份在认证中间件（`server/src/middleware/auth.js` 的 `PUBLIC_PATHS`），一份在组织上下文中间件（`server/src/middleware/orgContext.js` 的 `ORG_CONTEXT_BYPASS_PATHS`）。新加的网页退出登录只补了第一份，请求过了认证却卡在第二份，处理函数始终没被执行。

现在靠什么防止再发生：必须跑的检查 `node server/test/publicRouteBypass.test.js`——它会核对“认证免检的入口必须同时免组织上下文”，并逐个调用两个中间件确认请求真的能穿过去；`/api/ping` 与 `/api/health` 因为在认证之前就已注册，单独核对它们的注册顺序。

怎么判断又犯了：新增任何公开接口后，直接不带凭证请求它一次，看返回的是接口自己的应答，还是“请先登录”或“请重新选择组织和工作角色”。

### 坑 19：网页的玻璃模糊静默失效，卡片看起来像普通白底后台

你会看到什么：网页的门户、消息、审核等页面卡片是平的白色块，没有小程序那种玻璃质感；同一套色值、同一套圆角，观感仍然差一截。

为什么：打包压缩把同一条规则里的 `backdrop-filter` 和它的 `-webkit-` 前缀写法判成重复声明，只保留了前缀那条；而浏览器读到的计算值是 `none`，等于模糊从来没生效。源码里两行都在，肉眼看不出问题，只有读浏览器算完之后的值才能发现。

现在靠什么防止再发生：必须跑的检查 `node web/scripts/parity-audit.mjs`——它用真实浏览器读最终生效的样式值（三档断点各 29 项），`backdrop-filter` 必须是 `blur(12px)`；样式里标准属性单独声明，前缀版本只放在 `@supports` 里。

怎么判断又犯了：打开网页门户，看卡片有没有玻璃模糊；或者在浏览器控制台执行 `getComputedStyle(document.querySelector('.card')).backdropFilter`，正常值应当是 `blur(12px)`。

### 坑 20：网页底部显示了当前登录组织，和小程序的固定品牌不一致

你会看到什么：小程序底部两行是"WHUSU智慧工作台""武汉大学学生会"；网页底部第二行却显示当前组织，线上成了"武汉大学第四十四届学生会"。

为什么：小程序底部第二行取的是语言库常量 `common.organizationName`（固定品牌），不是当前登录组织；网页一开始写成读取会话里的组织名，于是跟着数据库里的组织名变了。这是"取值来源搞错"，不是文案写错，所以文案审计拦不住。

现在靠什么防止再发生：网页底部（门户、登录、工作台、评分任务、场地管理）统一引用共享语言库的 `common.organizationName`；浏览器测试里加了断言——底部第二行必须等于语言库常量，且不得等于当前登录组织名。

怎么判断又犯了：用一个组织名与"武汉大学学生会"不同的账号登录，看底部第二行是否仍是"武汉大学学生会"；页面内"当前组织与工作角色"卡片显示当前组织是对的，两者不要混。

### 坑 21：两端各存一份文案，改一边就分叉

你会看到什么：同一个按钮、同一句提示，小程序和网页说法不一样（例如小程序"待办事项"、网页"待办"），或者改完小程序忘了改网页。

为什么：最初网页语言文件是另写的一份，和小程序的文案靠人工同步，必然走偏。

现在靠什么防止再发生：文案唯一来源是 `shared/locales/zh-CN/**`；`node scripts/sync-shared-modules.js` 校验两端副本逐字节一致（不一致直接失败），`node scripts/locale-align.js` 把网页语言文件生成为对共享库的引用，`node scripts/locale-single-source-audit.js` 拦截任何想在网页自存文案的文件；三条都已接入 CI。网页语言文件与业务代码里出现中文同样会被 `--localization-prefix=web/ --strict-localization` 拦下。

怎么判断又犯了：跑 `node scripts/locale-single-source-audit.js` 与 `node scripts/sync-shared-modules.js`，任一失败即说明又出现第二份文案；`cd web && node scripts/parity-content-audit.mjs` 会逐页列出两端说法不一致的条目。

### 坑 15：本地和线上不一样

- 编译固定关掉 `nodeModules`、`es6`、`enhance`、`swc`，不许依赖微信开发者工具热重载注入的编译辅助代码；引入新语法前必须确认辅助代码真的被打进包里。
