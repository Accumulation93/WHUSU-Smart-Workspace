# 交付说明写作规范（管“我跟你说话”的字）

## 为什么需要这份文件

项目对“给最终用户看的界面文字”有很硬的规则：文案必须放在语言文件里、禁止内部术语、禁止碎片词句，`scripts/copy-quality-audit.js` 与 `scripts/user-visible-copy-audit.js` 会去检查。但这些检查只扫语言文件和小程序/服务端代码，**规范文档、技能文档、以及我在对话里给你的说明都不在检查范围内**。

结果就是：文档本身是“规格书语言”（大量名词堆叠、省略主语），我照着它的词表跟你说话，你就看到一堆看不懂的词、语病和短句。这份文件专门管这一件事，只约束我给你的字，不约束界面文案和代码注释。

## 七条规则（每条先说为什么，再说怎么做）

**1. 先给结论，再给依据。**
先说结果，让你决定要不要往下看；再说事实、数字和出处。不要把结论藏在最后一段。

**2. 用“你/我”，写完整句子。**
省略主语的句子读起来像标题，也容易产生歧义。不要写“已完成排查”，要写“我排查完了，结论是没有请求失败”。

**3. 不许使用只有读过内部文档的人才懂的词。**
如果必须指某个检查脚本，就写“必须跑的检查：`scripts/xxx.js`”。下表里的词在跟你会话时不要单独出现；确实需要提到时，用右边那句话，或者先用一句人话解释。

| 内部说法 | 跟你说话时怎么写 |
|---|---|
| 门禁 / 闸门 | 必须通过的检查（后面跟上脚本名） |
| 兜底 | 出问题时保底的做法 |
| 收敛 | 得出明确结果，不能停在中间状态 |
| 不变式 | 任何情况下都必须成立的条件 |
| 口径 | 统一的计算或展示规则 |
| 契约 | 约定（接口约定、数据结构约定） |
| 落盘 | 写入存储 |
| 静默 | 没有提示、悄悄发生 |
| 触底 | 滚动到底部 |
| 幂等 | 重复执行结果相同 |
| 快照 | 某个时刻的数据备份 |
| 原子切换 | 一次性切换，中间不出现半成品状态 |
| 自愈 | 自动修复 |
| 复盘 | 事后分析 |
| 预检 | 正式操作前的试跑检查 |
| 裁剪 / 截断 | 内容被切掉一部分 |

**4. 每条结论都要有数字和出处。**
不写“响应较慢”，要写“这个接口当天被调用 434 次、其中 18 次被客户端中断（来源：Nginx 访问日志）”。

**5. 不写电报体。**
不写“5xx=0，检查通过，已闭环”。写成：“这次发布期间没有任何请求失败，部署日志和访问日志里都是 0 条失败记录。”

**6. 长内容要分组，篇幅要克制。**
默认不超过十行；超过十行就分三到五个小标题，每组四到六条；不要嵌套列表，不要一段塞三件事。

**7. 结尾讲清“做完了什么、还剩什么”。**
不许用“已闭环”“已落地”这类抽象收尾。要说清：做了什么、什么时候做的、你还需要做什么、我没能验证的是什么。

## 写完自己过一遍的六问

1. 有没有哪句话没有主语，读起来像标题？
2. 有没有出现上表左侧的词而没有翻译？
3. 每条结论后面有没有具体数字或文件名？
4. 有没有把完整句子砍成短片的写法？
5. 超过十行有没有分组？
6. 最后有没有说清楚还没做完的部分？

## 一个对照例子

不要这样写：

> 发布窗口 5xx=0，键盘契约门禁通过；残留风险：交付说明前需现场验收。

改成这样写：

> 这次发布期间没有任何请求失败，我核对了部署日志和访问日志，都是 0 条失败记录。弹窗和键盘的检查也通过了（`scripts/dialog-keyboard-audit.js`）。还需要你在手机上确认一遍实际手感，这一步我做不了。
