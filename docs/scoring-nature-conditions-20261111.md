# 评分规则的岗位性质条件

## 存储与旧版兼容

`rate_target_rules.nature_ids` 限制评分人岗位性质；`rate_rule_clauses.nature_ids` 限制被评分人岗位性质。两列均为可空 JSON 数组。迁移 `20261111102000_scoring_rule_natures.sql` 只增加列，不更改现有规则或评分记录。NULL 表示原规则不限岗位性质，空数组不是不限。

API 使用顶层及每个 clause 的 `natureIds`。原有 `scorer_key` 仍按部门、身份类别建立，性质集合限制同一类别内的岗位，不另建平行评分规则。保存时在事务内检查组织、性质及适用身份；旧版未传性质时保留同一规则和可唯一对应条款的限制，不能将新限制改成不限。

两端配置先选择性质，再显示适用身份的并集。切换性质造成已选身份不适用时先确认，取消保留原选择。旧不限规则必须明确选择性质，保存前确认范围变化。批量套用条款要求被操作规则和条款已经明确性质，不能借批量操作绕过范围确认。

## 计算与读取

评分目录、打开评分表、提交、评分任务统计、结果中的当前任务统计，以及待办共用相同性质条件。人员本身的岗位有效性继续由 participants 的统一关联检查执行。

待办索引仍先按范围定位候选，再按该范围的性质分支筛选。只有不限性质的全员分支可以覆盖其他范围；受限全员分支不能吞掉其他性质的部门分支。

显式性质条件的首次评分写入 v3 计算快照，双方性质集合参与策略摘要。未配置性质的旧规则仍生成原 v2 格式；现有 v1/v2 的字段投影和摘要算法不变，不改写历史记录。读取同时接受 v1、v2、v3；v3 条件被删除、修改或结构不合法时验证失败。
