# 统一授权实施记录

更新：2026-11-02。本轮方案与完整本机 CI 已获用户批准。以下记录主项目代码和本机专项验证事实，不表示生产已切换或已发布。

## 当前实现

新授权路由已在 `server/src/index.js` 注册。两端共用服务端统一授权模块，数据库默认 `shadow`；正式启用通过发布协调器进行，不能把隔离库的 `enforced` 当成生产状态。

规则表达授权对象、操作、数据范围、字段和生效条件。当前岗位或管理身份单独判断，不合并同一人的其他工作角色。能力目录登记具体动作，方案保存具体能力，不使用会自动覆盖未来功能的通配授权。禁止优先，未知条件不产生授权；指定审批人、印章资格、组织边界和历史保护仍是必需条件。

`authorizationBusinessRoute.js` 登记已适配与明确退役入口。部署检查根据原路由权限目录核对遗漏，未覆盖入口阻断激活。业务接入覆盖人事、审核、场地、评分、通讯录、日程、通知、身份卡及系统管理；静态登记不能替代下面的业务验证。

### 人事与账号治理

- 目录、详情、岗位面板、补充资料维护和审核、导入与导出已接入。动态字段使用 `profile:<fieldId>`，规则保存核对本组织生效字段，模板切换与字段授权使用同一组织字典锁。学号和敏感字段只允许管理身份在人事专用入口读取。
- 保存仅更新明确提交的获授字段，未读字段不能被空值覆盖。整份待审资料所需字段必须在同一岗位范围获准；按钮和实际提交一致。门户待办逐角色核验，不将跨角色汇总用于写入。
- 成员新增、离任、重新加入和组织范围永久删除在原事务复核。`auth.persons.delete` 保留超管硬限制；普通获授权管理员原有账号管理能力继续迁移，不错误降为仅超管。
- 账号、认证和恢复分别返回最小资料与 `canGlobalAccountManage/canVerifyIdentity/canRecoverAccount`。认证、恢复请求编号限定当前组织；恢复能力只取得恢复码是否存在，不取得码值。人事资料读取不附带账号治理。
- 全局模板定义维持共享，组织选用和说明独立。`hr.profileMigration` 管理已有个人资料迁移，与配置复制分开：目标角色提交、来源角色批准，未批准不下发来源值，执行时重查请求授权。缺少可信授权信息的旧待审申请要求重提，不猜测补权。
- 旧导入和跨组织迁移在实际写事务锁定旧模式；迁移申请、结果和明细同事务提交，不能在启用后继续使用先前的旧判权。

### 审核、场地、日程、通知与身份卡

- 审核模板、印章、验签配置与使用、申请和附件读取、创建、编辑、重提、撤回、审批及删除分别核验。管理权不代替指定岗位处理资格，明确禁止不能被原验签名单绕过。
- 场地资源、开放时间、周期占用、借用规则、流程及审批分别登记。共享时间仍要求场地全局配置资格；不可读的借用以匿名占用保留，不释放冲突时段。取消和提前结束在锁定记录后重查。
- 配置候选与完整资源分离。`configurationVenues` 仅返回获授配置所需编号和名称，不附带完整资源资料；评分配置的部门、身份、岗位候选同样只返回必要信息。
- 日程和参会名单、手机订阅及来源记录应用统一判断。订阅凭据只解析有效只读角色，不用于写入。通知和待办列表、计数同步过滤，未读和全部已读不再以固定条数截断。
- 身份卡本人读取、成码和公开核验已接入。扫码人无需登录，限制作用于码持有人；成码期间撤权和旧码核验重新检查，未获准不返回资料。

### 评分

- 活动、模板、规则、公示、成绩和导出按动作、记录及字段判断。切换当前活动同时核验原活动和新活动；模板复制要求完整来源读取及目标创建权。
- 最终分保留完整输入，仅在某目标全部原始评分记录可读时返回，不把部分可见记录算成最终分。诊断和缓存包含授权范围，响应前复核角色和版本。
- `scoring.tasks.read/export` 独立表示评分岗位任务，不从成绩记录推导。普通评分、修改和评优保留原资格并追加统一禁止，写事务重新核验。

## 两端界面

两端提供分配权限、授权身份、查询权限三个页签及独立编辑页。“授权身份”是可复用权限方案的界面名称，独立于人事身份类别，不修改岗位字典。日常新增按“选择岗位或管理员 → 选择授权身份 → 选择记录范围”填写；只允许选择已发布身份，重要删除、导出及治理能力仍明确展示，保存仍先预览影响。

权限分配入口由服务端的 `canManageAuthorization` 控制，普通岗位只有获得当前有效委托后才开放，不再按管理员类型直接排除。委托受领工作角色与可获授权对象分开保存；普通岗位委托不包含治理能力，不能转授分配资格或修改命中自身的规则。方案发布及恢复逐条复核关联规则，同样禁止间接改变自身授权。动态目标条件不能转换为调岗后仍生效的固定岗位授权；显式岗位候选只来自委托中的显式集合，动态条件通过同形或更窄的规则使用。只读查询入口单独由 `canInspectAuthorization` 表达，不附带分配权。

人员授权按明确的岗位或管理身份编号分组，不按姓名合并，不混入其他岗位权限。多人共用规则标明修改影响全部授权对象。动态人群、禁止规则、自定义字段、期限和记录范围完整保留在“全部授权规则”和高级设置；不能完整表达的既有规则自动打开高级设置，禁止折叠时清空限制。旧规则不自动转成猜测的授权身份。支持发布、历史版本恢复、委托、批量选择和删除。实际权限候选逐角色授权，不下发自然人编号；只获查询权时不读取配置目录。

管理入口消费 `getCurrentAuthorizationAccess.grantedCapabilities`，普通业务关系不产生管理入口。普通人事、审核和评分工作台在原子应用显示获授管理页签；原生正式 Behavior 和管理组件复用，网页使用相同服务端能力。页面隐藏、退出、切换工作角色清理结果并拒绝迟到响应。

动作依据逐记录、字段能力显示，不能只看入口权限。人员选择复用共享组件，岗位一岗一卡、自然人一人一卡。最后一轮模板、公示、迁移面板和治理调整必须纳入最终网页与微信验收，不能用此前模拟响应通过替代最终版本。

## 旧权限迁移与发布

`authorizationLegacyPlan` 和 `authorizationLegacyMigration` 在 shadow 暂存旧管理员实际有效权限，仍归原管理身份。旧未勾选不是禁止，旧删除权附带的读取保留；新增分享、接收、分配权不能从维护权推导。委托有明确边界且不能转授；未知旧配置和人工修改的迁移规则阻断转换。

`authorizationCutover.stageAll()` 暂存全部组织。`activate()` 要求两个不同真实兼容提交；发布工具核对当前链接、实际 PM2 进程目录、发布文件、协议和回退版本。事务内再次对比全部组织旧摘要、转换规则和委托，来源变化、未审阅人工规则或缺失组织均拒绝。

全组织授权模式与场地事由组织化在同一事务启用。`authorization_runtime_transition` 保存协议、当前/回退提交和对照结果，新建组织持共享锁并继承启用状态。旧事由在兼容阶段仍读写原表，启用等待在途操作并重新复制最新内容，不使用早期副本代替最新资料。

切换锁顺序为全局启用记录、事由存储阶段、组织与授权行；旧事由写入先取阶段锁再取组织锁，不能倒置。隔离数据库的两个并发连接验证旧写入持阶段锁时仍可取得组织锁并提交，随后切换完成；新建组织先持全局共享锁，不会遗漏在整轮启用之外。

生产顺序是先上线兼容解释器，再建立第二个已验证兼容发布，随后暂存、对照和激活。启用后禁止回退不理解新规则的版本；恢复方案通过新版本发布，不覆盖历史。旧权限管理只读，旧写入口返回升级提示。旧存储尚未删除，须正式切换和兼容回退演练后独立迁移处理。

第二版的协议文件明确登记 `activationReady:true`，发布协调器只允许当前实际运行版本具有首次启用资格；回退版仅要求协议兼容，不因缺少该标志被排除。协议内容必须与对应提交中的文件一致，临时修改release文件不能获得启用资格。此标志不能代替全部组织差异核对、实际进程目录检查及独立兼容回退版本。首次启用只运行第二版当前链接下的协调器；启用后回退到第一版仅恢复运行，不再次调用旧版stage/activate。两次发布本身不等于实际回退演练，相关结果分别记录。

配置复制要求来源明确分享、目标明确接收，不因同人在两边任职打通。规则先存草稿并核对关联，不复制账号、个人资料、审批历史、签名或印章；详见 `organization-config-copy.md`。

## 后续功能接入方法

1. 在 `server/src/core/services/authorizationCatalog.js` 按资源登记具体动作、允许的数据范围和字段。新能力不设置旧权限映射，除非已证明存在等价旧能力；业务参与资格只由领域模型提供，不能把前端布尔值当作依据。
2. 在对应 Model 使用 `createAuthorizationSession`，传入认证中间件取得的当前工作角色。列表用 `queryScope` 限定查询，逐记录用 `check`，返回字段用 `project`。写入在同一事务锁定角色、授权和资源后重查，仍执行审批责任、组织和历史保护等业务限制。读取入口不能当作写入授权。
3. 为可按记录授权的资源在 `authorizationReferences.js` 登记本组织引用校验；新增补充资料使用 `authorizationProfileFields.js` 的字段目录，不绕过学号保护。必要候选另行返回最小资料，不能要求用户额外取得整个人事目录的读取权。
4. 完整接入后才在 `authorizationBusinessRoute.js` 登记路由，保留旧模式的已验证业务分支。更新 `shared/authorizationAccessView.js` 和共享语言库，两端消费服务端能力显示入口；客户端显示不代替服务器检查。共享副本通过既有生成器同步。
5. 新增配置复制类型必须分别实现来源白名单、目标关联校验、保存回读和撤权检查，复用 `organizationConfigCopy` 的分享与接收流程。不可直接接收任意表名、SQL、人员编号或来源组织对象并写入目标。
6. 隔离库至少验证合法保存后回读、未授权、其他组织、同人不同岗位、字段不交叉泄露、撤权和失败整单回滚。迁移兼容性、两端实际操作、微信编译及是否运行完整 CI 依项目要求分别记录。新增能力不得自动扩大已发布方案。
