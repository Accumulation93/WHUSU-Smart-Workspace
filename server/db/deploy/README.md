# 自动部署迁移目录

本目录只存放由生产自动部署系统执行的新迁移，历史 `server/db/migrate_*.sql` 不会被自动重跑。

`server/db/migrate.sh`、`server/db/migrate.bat` 等旧入口仅为历史兼容工具，不是生产迁移入口；生产只读取本目录并通过部署账本执行。

规则：

- 文件名使用 `YYYYMMDDHHMMSS_description.sql`，按文件名顺序执行。
- 每个迁移必须可安全重试；迁移成功后才写入 `schema_migrations` 账本。
- 已执行文件禁止修改，部署会核对 SHA-256 并拒绝校验和不一致的文件。
- 允许破坏性 DDL，但部署会先进入维护状态并生成完整数据库快照；失败时自动恢复快照。
- 迁移不得包含数据库密码、用户凭据或测试数据。

## 发布方式与停机口径

- **默认在线发布（零中断）**：加列、建表、建索引、数据回填这类非破坏性迁移在服务
  运行时应用，只额外生成一份一致性快照（`mysqldump --single-transaction`），
  不停进程、不进入维护状态；随后在独立端口预检新版本，再用 PM2 集群**滚动重载**
  切换流量，单个实例失败会滚动切回旧版本，全程不中断对外服务。
- **破坏性迁移仍走维护窗口**：`DROP TABLE/DATABASE/COLUMN/INDEX`、`TRUNCATE TABLE`、
  `DELETE FROM`、`RENAME TABLE/COLUMN`、`ALTER TABLE ... MODIFY|CHANGE`，或在文件内
  声明 `-- @destructive`，都会被判定为破坏性；UTC 时间体系切换同样如此。这类发布
  会先停止 API/Worker/备份进程、生成完整快照再迁移，失败时自动恢复快照。
- **上线前预检**：任何服务端发布都会先用新版本在独立端口连上（迁移后的）数据库
  跑通 `/api/health`，预检失败即放弃本次发布，线上版本与维护状态都不受影响。
- 因此“升级必然中断”已被消除：只有破坏性 DDL 与 UTC 切换才需要维护窗口。
